# 官方流程 500 MHz 优化过程（2026-11-26）

起点 `d93507a` · 终点 `dd690a8` · 课程框架 `302f0cf3` · 性能程序 latency=10

**主工程默认配置现在用课程官方 `make synth` 得到 32,672 μm²、IPC 1.1175、536.97 MHz，三项同时满足 Tier3，频率过 500 MHz 加分线。** 起点是 37,981 μm²、IPC 1.1153、338.07 MHz，面积超限。指令窗口和缓存容量没有改动，也没有增加流水级。

**536.97 MHz 需要 `config.mk` 里的 `CLOCK_PERIOD_NS ?= 1.0`。** 框架默认的 2.0 ns 目标下，同一份源码是 475.62 MHz。第 3 节说明这个参数做了什么、为什么默认目标到不了 500 MHz。评测若只用框架默认参数，得分对应 475.62 MHz。

完整测量见[测量报告](course_D1000_F537_2026-11-26.md)，网表与证据见 [versions/course_D1000_F537](../versions/course_D1000_F537/README.md)。

每一步都跑了六项性能程序和 19 项正确性程序（RTL 仿真），正确性全部通过。

## 2. 设计改动

### 2.1 去掉 `keep` 和 `keep_hierarchy`

起点的 RTL 有 41 处 `keep`/`keep_hierarchy`，用来保住手写的扇出树和若干小模块的边界。官方流程是 `synth -flatten` 后整体交给 ABC，这些属性让约 5 万个反相器实例和约 80 个子模块留在各自的边界里：跨边界的逻辑不能合并，ABC 也不能对这些树重新缓冲。全部去掉后，默认流程的组合面积从 22,438.7 降到 17,391.1 μm²，频率从 338.07 升到 387.15 MHz。时序面积同时从 7,598.8 降到 7,451.8 μm²，应是保留属性原先阻止了一部分触发器被合并或删除。

2026-10-31 的优化分析把官方流程面积超限的第一候选放在 PRF 改用 SRAM 上。实测面积问题不在某个模块的存储实现：去掉层级约束一项就省了 5,195 μm²，PRF 没有改。

### 2.2 SRAM 宏引脚的独立驱动

去掉层级后，最差路径的终点全部落在 SRAM 宏的输入引脚上。原因在流程本身：FakeRAM 宏每个输入引脚的电容是 5 fF，相当于 9 个左右的标准单元输入；而 ABC 把通往宏的网络一律当作**一个** 5 fF 的输出来选驱动，不管这条网络实际接了多少个宏引脚。例如取指行过滤的片选路径上，一个最小号缓冲单元实际带着 45 fF，STA 在这一级算出 0.29 ns；D-cache 一路数据的地址线则要接 16 个宏。

新增 `rtl/common/rv32_sram_pin_tree.v`：每个宏引脚前放一个普通的 RTL 反相器，它驱动的正好是 ABC 假设的一个 5 fF；上游逻辑只看到普通的门输入负载。树的另一级反相在引脚数少时交给普通逻辑，引脚数多时每 8 个引脚放一个根反相器。这个反相器模块是设计里唯一保留 `keep_hierarchy` 的地方，否则两级反相会被消掉，引脚又合到一个驱动上。共 1,212 个实例，各映射成一个 INVx1，合计 53 μm²。

使用位置：I-cache 数据阵列、取指行过滤、D-cache 数据和标签、AXI 读前缀。两处同时调整了宏的接法，功能不变：

- D-cache 数据字节的片选原先由官方封装在宏外面算（`en & (~we | wmask)`），现在在 RTL 里按字节算好，`wmask` 恒为 1，写掩码不再经过封装里的那一级门。
- AXI 读前缀原先是一个 96 位、32 位写粒度的 SRAM，官方封装把它展开成 3 个 1×32 宏；现在直接例化 3 个，写入时只使能被写的那一个。宏的数量、形状和面积不变。

这一步之后默认流程是 458.78 MHz。

### 2.3 启用已有的时序策略参数

仓库历史里有一批默认关闭的时序参数，各自有审阅文档（`docs/*_review_2026-10-*.md`），当时在带层级约束的 RTL 上逐组测过，频率在 331 到 394 MHz 之间，没有达到 500 MHz 的采用门槛，于是留在了关闭状态。清理前提交 `8837b2f` 的 `configs/tier3_shared_500_range_carry_mdu_candidate.json` 是其中最快的一组，当时测得 393.998 MHz。在去掉层级约束的 RTL 上把这 36 个参数作为默认值，六项周期数一个不变，频率 458.78 → 475.39 MHz，时序面积从 7,451.8 降到 6,984.7 μm²。

另一组更大的组合（`completion_load_packet_fold_candidate`，38 个参数）是 470.80 MHz，没有采用。

### 2.4 I-cache 数据阵列拆成 16 位宏

上一步之后，1.0 ns 目标下的最差路径从 I-cache 的 128×128 数据宏出发，经取指响应、预测器、取指队列容量判断，回到 I-cache 请求队列。FakeRAM 模型的读出延迟是 `0.071 + 0.0000167×深度 + 0.00124×单宏位宽` ns，面积按位计。128 位的一个宏读出要 0.233 ns，换成 8 个 16 位宏是 0.093 ns，面积同为 687.97 μm²。8 个宏接同一组命令，各引脚走 2.2 节的独立驱动。1.0 ns 目标下 518.48 → 533.06 MHz。

D-cache 的数据宏本来就是 8 位，标签是 19 位，没有可拆的余地。

### 2.5 关闭六个旁路

对 `student_top` 的参数逐个做了 IPC 敏感度扫描（第 4 节）。六个开关关掉后 IPC 不降：`PREDICTOR_PREFIX_QUERY_HISTORY`、`RAT_READ_BYPASS`、`RECOVERY_ROB_CREDIT`、`DCACHE_HIT_RESPONSE_COISSUE`、`DISPATCH_FULL_REPLACE`、`LSQ_SECOND_REPORT_RECLAIM`。一起关掉后 IPC 从 1.115263 到 1.117497，1.0 ns 目标下 533.06 → 536.97 MHz，2.0 ns 目标下 479.63 → 475.62 MHz。后者下降在 ABC 目标附近属于映射噪声的量级；采用的依据是 IPC 和 1.0 ns 目标的结果。

## 3. ABC 延迟目标

`make synth CLOCK_PERIOD_NS=x` 是课程 README 给出的参数。它在官方脚本里有两个用处：作为 ABC 的 `-D`，以及作为 OpenSTA 报告裕量时的参考周期。**报告的频率不取决于后者**：`timing.tcl` 对最小周期做二分搜索，输入输出延迟、不确定度和负载都是固定值。所以这个参数对频率的影响只通过 ABC 的映射。

ABC 的受约束脚本是 `… &nf -D; buffer; upsize -D; dnsize -D`。在 `a112d5d` 上逐步打印它自己的延迟估计：

| ABC 步骤之后 | 目标 2.0 ns | 目标 1.0 ns |
| --- | ---: | ---: |
| `&nf` 映射 | 51,865 ps | 51,865 ps |
| `buffer` | 2,543 ps | 2,543 ps |
| `upsize` | 1,954 ps | 1,765 ps |
| `dnsize` | 1,990 ps | 1,765 ps |
| OpenSTA 最小周期 | 2,085 ps | 1,876 ps |

两点决定了结果。第一，`upsize` 一达到目标就停，`dnsize` 再把余量换回面积，所以 2.0 ns 目标下 ABC 停在它自己估计的 1,990 ps。第二，ABC 的估计不含触发器的时钟到输出延迟、建立时间和 0.05 ns 的时钟不确定度，比 OpenSTA 少约 0.1 ns。两者相加，2.0 ns 目标的结果必然落在 2.1 ns 附近，也就是 475 MHz 上下，与设计本身还能不能更快无关。

把目标设到 ABC 达不到的值，`upsize` 就一直做到没有改进为止。目标取 0.5 到 1.6 ns 的五个值，结果完全相同（533.06 MHz，同一面积）；1.8 ns 是 505 MHz，1.9 ns 是 493 MHz（这两个数在 `49586a5` 上测得）。加大尺寸的代价是 19 μm²。

在 2.0 ns 目标下能不能靠别的官方参数过 500？试了 `ABC_LOAD_FF`：40 / 100 / 250 fF 分别是 476.94 / 482.56 / 486.92 MHz，面积涨到 34,496 / 35,201 / 35,998 μm²。到面积上限也没到 500。把驱动单元换成更弱的 INVxp33，2.0 ns 目标下频率不变。结论是：**在框架默认目标下，这个设计到不了 500 MHz；要到 500 需要评测接受 `config.mk` 里的 `CLOCK_PERIOD_NS`。**

README 允许的另一组参数 `ABC_DRIVING_CELL=BUFx2_ASAP7_75t_R ABC_LOAD_FF=0.56`（上一个冻结版本用过）在 `a112d5d` 的 1.0 ns 目标下是 525.40 MHz、32,069 μm²，比同一提交的默认驱动设置面积少 614 μm²，频率低 7.7 MHz。没有采用，`config.mk` 只改了一个参数。

## 6. 现在的关键路径

1.0 ns 目标下，2.0 ns 周期内最差的四组路径裕量在 0.138 到 0.156 ns 之间：

1. AXI 数据响应 FIFO → D-cache 响应 → LSQ 返回唤醒 → RS 操作数旁路 → RS 发射选择 → ALU 结果寄存器。
2. 同一起点 → RS 占用计数。
3. AXI 指令响应 FIFO → I-cache 未命中记录的地址字段。
4. LSQ 地址字段 → 请求选择 → store 转发判定 → LSQ 载荷寄存器。

四组裕量接近，继续提高频率需要同时处理内存响应当拍唤醒和 LSQ 当拍选择加转发，单改一处收益有限。

## 7. 没有验证的部分

- **评测方式。** 536.97 MHz 是否计分取决于评测是否使用仓库的 `config.mk`。这一点无法在本机确认。
- **Tier1 / Tier2 的面积和频率**没有重新综合。两个档位的周期数与冻结记录相同，但去掉层级属性会改变它们的映射结果，10 月的面积和频率数值不能当作当前源码的结果。
- **没有做形式等价检查。** 依据是 RTL 与门级的功能回归。
- **工具是本机从源码构建的**，版本与课程 Dockerfile 固定的一致，不是课程 AppImage 的二进制。在未改动的起点上复现了 10 月报告的面积、频率和全部周期数。
- STA 是理想时钟、无布线寄生的估计，这是课程评估条件，不是布局布线后的频率。

## 8. 复现

```sh
tools/build_pinned_course_tools_linux.sh all ~/cpu2026-tools   # 约 15 分钟，仅在没有 AppImage 时需要
make synth YOSYS=… ABC=… STA=… ASAP7_LIB=… APPIMAGE=
make build && make perf LATENCY=10 && make test MAX_CYCLES=1000000000
```

`tools/staged_course_synth.py` 是第 1 节提到的分阶段流程，换一个 ABC 参数只需重跑映射和 STA（约 7 分钟），并把触发器按 RTL 寄存器命名，便于读 STA 路径。它只用于探索，正式数字以 `make synth` 为准。
