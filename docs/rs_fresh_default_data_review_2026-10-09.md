# Fresh RS candidate payload before allocation confirmation

The combined Tier1 freeze `a7e64b80` measured 8962.127155 um² and 274.678112 MHz. It passes area but fails frequency. No CPU build/perf/smoke was run for that freeze; its IPC is unknown. The measured worst path starts at Icache SRAM output, goes through architectural source decoding, RAT/PRF preview, `d_replace_rs_demand`, ROB allocation acceptance, fresh RS packet masking, SUB control, and the integer adder. Endpoint `_116076_/D` is the registered integer value bit 31: mapped QN `_000829_` drives an inverter whose output is `alu_exec_value[31]`. Arrival is 3.5808 ns and the reported minimum period is 3.640625 ns. This is a measured allocation-control path, not a claim about every operand path.

`RS_FRESH_DEFAULT_LANE_DATA=1` is a default-off parameter of the same `student_top` → `cpu_core` → `rv32_backend_joint` → shared `rv32_reservation_station`. It requires the existing allocation issue bypass. It changes only the fresh payload selector's idle data convention. Original actual grants, incoming ready ranks, issue validity, stored-row selection, accepted allocation slots, and release accounting are unchanged.

For an issue lane, original grants are one-hot because each ready incoming lane receives a distinct accumulated rank. Let G be those actual grants. Fresh validity stays OR(G). For more than one allocation lane, data grants are `D[k]=G[k]` for k>0 and `D[0]=!OR(G[k>0])`. If G is nonzero and one-hot, D=G; therefore every valid fresh packet is bit-identical. If G=0, the candidate packet from lane 0 is visible but invalid. For one allocation lane, the same selector reduces to the lane 0 packet directly; there is no allocation-acceptance gate in front of opcode or operand data. No CPU implementation is selected by issue width; this is ordinary parameterized reduction of one selector.

The original `fresh_lane_allowed` still selects fresh versus saved data. Fresh recovery cancel/qualification sidebands remain zero. Stored issue payloads and wakeup selection are untouched. Actual allocation slot generation remains qualified and is retained in the packet. Simulation asserts one-hot grants and exact valid-packet equivalence to the original selector, using full original payload width.

Invalid raw data can change combinational functional-unit routing/ready. Backend MDU candidates include `rs_issue_valid`; ALU issue validity includes `rs_issue_valid` and routing; recovery age predicates include valid; RS issue fire/release requires valid and ready. Allocation fire in the supported no-release-credit mode depends on incoming allocation validity and saved capacity, not downstream issue ready. Thus idle data cannot create an accepted allocation or execution. Valid packets and those inputs' readiness are unchanged. The runner/core/RS reject enabling the policy without allocation issue bypass; the existing bypass guard requires direct static dispatch with no release credits or issue pipeline.

A single finite paired sample covers width 1/2 using the same RS and parameter values 0/1: invalid candidates, stalled fresh payload retention, immediately consumed fresh packets, older unready allocation followed by same-cycle wake, flush boundary, full-capacity rejection, reset and row reuse. It compares cycle-by-cycle actual valid/fire, complete valid packet (including full tag, physical destination, both operands, store data, metadata and slot), row ownership, occupancy, slots and release state. It is native two-state Verilator with WORD_SIM scheduling, not four-state or whole CPU proof. See `reports/Tier_shared_RS_fresh_data_protocol_2026-10-09.json`.

The new profile `configs/tier1_shared_fresh_data.json` adds this policy to the measured combined owner/tree profile.
